# Лекция 2. Коллективные и парные взаимодействия в MPI

## 1. Введение

**Тема лекции:** коллективные и парные взаимодействия в MPI.

**План:**
1. Коллективное взаимодействие:
   - Широковещательный обмен (`MPI_Bcast`)
   - Операции редукции (`MPI_Reduce`)
   - Пример: вычисление числа π
   - Рассылка и сбор данных (`MPI_Scatter`, `MPI_Gather`)
   - Пример: вычисление скалярного произведения
   - Взаимодействие «Каждый к каждому» (`MPI_Allgather`, `MPI_Alltoall`, `MPI_Allreduce`)
   - Синхронизация вычислений (`MPI_Barrier`)
2. Взаимодействие между двумя процессами:
   - Режимы взаимодействия (стандартный, синхронный, по готовности, буферизированный)
   - Неблокирующее взаимодействие
   - Совмещённые приём и передача сообщений (`MPI_Sendrecv`)

## 2. Коллективное взаимодействие

### 2.1. Широковещательный обмен (MPI_Bcast)

```c
int MPI_Bcast(void *buf, int count, MPI_Datatype type, int root, MPI_Comm comm);
```

- `buf` — адрес начала буфера с данными.
- `count` — число элементов в буфере.
- `type` — тип данных элементов.
- `root` — номер корневого процесса.
- `comm` — коммуникатор.

**Особенности:**
- Коллективная операция: должны вызвать все процессы коммуникатора.
- Буфер имеет разное назначение:
  - для `root` — источник данных,
  - для остальных — приёмник.
- Передаёт данные от корневого процесса всем остальным.

### 2.2. Операции редукции (MPI_Reduce)

```c
int MPI_Reduce(void *sendbuf, void *recvbuf, int count, MPI_Datatype type, MPI_Op op, int root, MPI_Comm comm);
```

- `sendbuf` — буфер с передаваемыми данными.
- `recvbuf` — буфер для результата (только для `root`).
- `count` — число элементов.
- `type` — тип данных.
- `op` — операция редукции.
- `root` — номер процесса, получающего результат.
- `comm` — коммуникатор.

**Базовые операции редукции:**

| Операция   | Описание                     |
| ---------- | ---------------------------- |
| MPI_MAX    | Максимальное значение        |
| MPI_MIN    | Минимальное значение         |
| MPI_SUM    | Сумма значений               |
| MPI_PROD   | Произведение значений        |
| MPI_LAND   | Логическое «И»               |
| MPI_BAND   | Побитовое «И»                |
| MPI_LOR    | Логическое «ИЛИ»             |
| MPI_BOR    | Побитовое «ИЛИ»              |
| MPI_LXOR   | Исключающее логическое «ИЛИ» |
| MPI_BXOR   | Исключающее побитовое «ИЛИ»  |
| MPI_MAXLOC | Максимум и его индекс        |
| MPI_MINLOC | Минимум и его индекс         |

**Особенности:**
- Коллективная операция: все процессы коммуникатора должны вызвать.
- Все вызовы должны содержать одинаковые `count`, `type`, `op`, `root`, `comm`.
- Результат получает только `root`.
- Операция выполняется поэлементно над сообщениями.

### 2.3. Пример: вычисление числа π

**Формула:**
\[
\pi = \int_{0}^{1} \frac{4}{1+x^2} \, dx
\]

**Метод прямоугольников:**
- Отрезок [0,1] разбивается на `n` интервалов.
- Каждый процесс вычисляет свою часть суммы (циклическая схема).
- Частичные суммы собираются с помощью `MPI_Reduce`.

**Код (слайды 12–13):**
```c
#include "mpi.h"
#include <math.h>

double f(double a) {
    return (4.0 / (1.0 + a*a));
}

void main(int argc, char *argv[]) {
    int ProcRank, ProcNum, done = 0, n = 0, i;
    double PI25DT = 3.141592653589793238462643;
    double mypi, pi, h, sum, x, t1, t2;
    MPI_Init(&argc, &argv);
    MPI_Comm_size(MPI_COMM_WORLD, &ProcNum);
    MPI_Comm_rank(MPI_COMM_WORLD, &ProcRank);
    while (!done) {
        if (ProcRank == 0) {
            printf("Enter the number of intervals: ");
            scanf("%d", &n);
            t1 = MPI_Wtime();
        }
        MPI_Bcast(&n, 1, MPI_INT, 0, MPI_COMM_WORLD);
        if (n > 0) {
            h = 1.0 / (double) n;
            sum = 0.0;
            for (i = ProcRank + 1; i <= n; i += ProcNum) {
                x = h * ((double)i - 0.5);
                sum += f(x);
            }
            mypi = h * sum;
            MPI_Reduce(&mypi, &pi, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
            if (ProcRank == 0) {
                t2 = MPI_Wtime();
                printf("pi = %.15f, Error = %.15f\n", pi, fabs(pi - PI25DT));
                printf("time = %f\n", t2 - t1);
            }
        } else {
            done = 1;
        }
    }
    MPI_Finalize();
}
```

### 2.4. Рассылка и сбор данных

#### MPI_Scatter — распределение данных

```c
int MPI_Scatter(void *sbuf, int scount, MPI_Datatype stype,
                void *rbuf, int rcount, MPI_Datatype rtype,
                int root, MPI_Comm comm);
```

- `sbuf`, `scount`, `stype` — параметры передаваемого сообщения (`scount` — число элементов, передаваемых каждому процессу).
- `rbuf`, `rcount`, `rtype` — параметры принимаемого сообщения.
- `root` — процесс, выполняющий распределение.
- `comm` — коммуникатор.

**Особенности:**
- Все процессы коммуникатора должны вызвать.
- Корневой процесс передаёт сообщения одинаковой длины (`scount`) из буфера `sbuf` всем процессам.
- Каждый процесс (включая корневой) получает сообщение длины `rcount = scount` в буфер `rbuf`.
- Если размеры сообщений различаются, используется `MPI_Scatterv()`.

#### MPI_Gather — сбор данных

```c
int MPI_Gather(void *sbuf, int scount, MPI_Datatype stype,
               void *rbuf, int rcount, MPI_Datatype rtype,
               int root, MPI_Comm comm);
```

- `sbuf`, `scount`, `stype` — параметры передаваемого сообщения.
- `rbuf`, `rcount`, `rtype` — параметры принимаемого сообщения.
- `root` — процесс, получающий результат.
- `comm` — коммуникатор.

**Особенности:**
- Все процессы коммуникатора должны вызвать.
- Корневой процесс получает от всех процессов сообщения одинаковой длины (`rcount`) в буфер `rbuf`.
- Каждый процесс (включая корневой) передаёт данные длины `count = rcount` из буфера `buf`.
- Для сообщений разного размера используется `MPI_Gatherv()`.

### 2.5. Пример: вычисление скалярного произведения

**Задача:**
\[
S = \sum_{i=1}^{n} a_i \cdot b_i
\]

**Параллельная реализация:**
1. Разбить векторы `a` и `b` на блоки.
2. Передать блоки процессам.
3. Вычислить частичные скалярные произведения.
4. Редуцировать частичные суммы в одном процессе.

**Код (слайды 19–20):**
```c
#include "mpi.h"
#include "stdio.h"

void main(int argc, char *argv[]) {
    double *a, *b;
    int i, n, ProcNum, ProcRank;
    double sum, sum_all;
    MPI_Init(&argc, &argv);
    MPI_Comm_size(MPI_COMM_WORLD, &ProcNum);
    MPI_Comm_rank(MPI_COMM_WORLD, &ProcRank);
    if (ProcRank == 0) {
        scanf("%d", &n);
        a = new double[n];
        b = new double[n];
        // инициализация векторов a и b
    }
    MPI_Bcast(&n, 1, MPI_INT, 0, MPI_COMM_WORLD);
    n = n / ProcNum;
    if (ProcRank != 0) {
        a = new double[n];
        b = new double[n];
    }
    MPI_Scatter(a, n, MPI_DOUBLE, a, n, MPI_DOUBLE, 0, MPI_COMM_WORLD);
    MPI_Scatter(b, n, MPI_DOUBLE, b, n, MPI_DOUBLE, 0, MPI_COMM_WORLD);
    sum = sum_all = 0;
    for (i = 0; i < n; i++)
        sum += a[i] * b[i];
    MPI_Reduce(&sum, &sum_all, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
    if (ProcRank == 0)
        printf("\nInner product = %10.2f", sum_all);
    MPI_Finalize();
    delete [] a;
    delete [] b;
}
```

### 2.6. Взаимодействие «Каждый к каждому»

#### MPI_Allgather — сбор данных всеми процессами

```c
int MPI_Allgather(void *sbuf, int scount, MPI_Datatype stype,
                  void *rbuf, int rcount, MPI_Datatype rtype,
                  MPI_Comm comm);
```

- Все процессы получают собранные данные.
- Для сообщений разного размера — `MPI_Allgatherv()`.

#### MPI_Alltoall — обмен данными между всеми процессами

```c
int MPI_Alltoall(void *sbuf, int count, MPI_Datatype stype,
                 void *rbuf, int rcount, MPI_Datatype rtype,
                 MPI_Comm comm);
```

- Каждый процесс отправляет данные каждому другому процессу.
- Для сообщений разной длины — `MPI_Alltoallv()`.

#### MPI_Allreduce — редукция с результатом у всех процессов

```c
int MPI_Allreduce(void *sendbuf, void *recvbuf, int count,
                  MPI_Datatype type, MPI_Op Op, MPI_Comm comm);
```

- Результат редукции получают все процессы коммуникатора.

### 2.7. Синхронизация вычислений (MPI_Barrier)

```c
int MPI_Barrier(MPI_Comm comm);
```

- Коллективная операция.
- Выполнение процесса приостанавливается до вызова `MPI_Barrier()` всеми процессами коммуникатора.

## 3. Взаимодействие между двумя процессами

### 3.1. Режимы взаимодействия

#### Стандартный режим (MPI_Send)
- Отправляющий процесс блокируется на время выполнения функции.
- Буфер можно использовать повторно после завершения.
- Состояние сообщения может быть разным: в отправляющем процессе, передаётся, хранится в принимающем, принимается.

#### Синхронный режим (MPI_Ssend)
- Функция передачи завершается только после подтверждения от принимающего процесса о начале приёма.
- Самый медленный, но самый надёжный.
- Рекомендуется для длинных сообщений.

#### Режим «по готовности» (MPI_Rsend)
- Может использоваться, только если процесс приёма уже инициирован.
- Формально самый быстрый, но используется редко.
- Буфер можно использовать повторно после завершения.

#### Буферизированный режим (MPI_Bsend)
- Использует дополнительный буфер для копирования сообщений.
- Функция отправки завершается сразу после копирования в буфер.
- Требует создания буфера:
  ```c
  int MPI_Buffer_attach(void *buf, int size);
  ```
- После завершения операций буфер отсоединяется:
  ```c
  int MPI_Buffer_detach(void *buf, int *size);
  ```
- Рекомендуется для коротких сообщений.

### 3.2. Неблокирующее взаимодействие

- Блокирующие функции блокируют выполнение до завершения.
- Неблокирующие функции позволяют совмещать коммуникацию и вычисления.
- Имена неблокирующих функций имеют префикс `I` (Immediate):
  ```c
  int MPI_Isend(void *buf, int count, MPI_Datatype type, int dest,
                int tag, MPI_Comm comm, MPI_Request *request);
  int MPI_Issend(...);
  int MPI_Ibsend(...);
  int MPI_Irsend(...);
  int MPI_Irecv(...);
  ```

**Проверка завершения:**
```c
int MPI_Test(MPI_Request *request, int *flag, MPI_Status *status);
```
- `flag` = true, если операция завершена.
- Неблокирующая функция.

**Блокирующее ожидание:**
```c
int MPI_Wait(MPI_Request *request, MPI_Status *status);
```

**Дополнительные функции:**
- `MPI_Testall` — проверка завершения всех операций.
- `MPI_Waitall` — ожидание завершения всех операций.
- `MPI_Testany` — проверка завершения хотя бы одной операции.
- `MPI_Waitany` — ожидание завершения любой операции.
- `MPI_Testsome` — проверка завершения всех разрешённых операций.
- `MPI_Waitsome` — ожидание завершения хотя бы одной операции и оценка состояний всех.

### 3.3. Совмещённые приём и передача сообщений

```c
int MPI_Sendrecv(void *sbuf, int scout, MPI_Datatype stype, int dest, int stag,
                 void *rbuf, int rcount, MPI_Datatype rtype, int src, int rtag,
                 MPI_Comm comm, MPI_Status *status);
```

- `sbuf`, `scout`, `stype`, `dest`, `stag` — параметры передаваемого сообщения.
- `rbuf`, `rcount`, `rtype`, `src`, `rtag` — параметры принимаемого сообщения.
- `comm` — коммуникатор.
- `status` — результат выполнения.

**Вариант с одним буфером (если типы совпадают):**
```c
int MPI_Sendrecv_replace(void *buf, int count, MPI_Datatype type,
                         int dest, int stag, int source, int rtag,
                         MPI_Comm comm, MPI_Status *status);
```

## 5. Дополнительные сведения из транскрибации

### 5.1. Общая информация о MPI
- MPI — это стандарт и библиотека для разработки параллельных программ для систем с распределённой памятью.
- Стандарт описывает программный интерфейс (API), который должны реализовывать библиотеки.
- Реализации MPI бывают свободно распространяемые и коммерческие.
- Стандарт поддерживает языки C, Fortran, C++.
- Существуют оболочки для других языков (Python, C# и др.).
- До 5-го стандарта обеспечивалась совместимость на уровне исходного кода; с 5-го стандарта добавлена бинарная совместимость.

### 5.2. История стандарта MPI
- 1992 — начало исследований.
- Ноябрь 1992 — публикация рабочего варианта MPI-1.
- Ноябрь 1993 — обсуждение на конференции Supercomputing'93.
- 5 мая 1994 — окончательный вариант MPI-1.0.
- 12 июня 1995 — MPI-1.1.
- 18 июля 1997 — MPI-2.
- 21 сентября 2012 — MPI-3.
- 4 июня 2015 — MPI-3.1.
- 9 июня 2021 — MPI-4.0.
- 2025 — MPI-5.0 (ожидается).

### 5.3. Модель программирования
- Одна программа (SPMD — Single Program Multiple Data).
- Запускается на нескольких процессах.
- Каждый процесс имеет своё адресное пространство.
- Количество процессов фиксируется при запуске (в MPI-2 появилась возможность добавлять процессы).
- Каждый процесс имеет уникальный ранг (номер).
- Все процессы по умолчанию входят в коммуникатор `MPI_COMM_WORLD`.

### 5.4. Четыре концепции MPI
1. **Тип операции передачи данных** — парные или коллективные.
2. **Тип данных** — описание пересылаемых данных.
3. **Коммуникатор** — объект, объединяющий группу процессов и контекст.
4. **Виртуальная топология** — логическая топология связей между процессами (по умолчанию — полный граф).

### 5.5. Сложность разработки
- Объём дополнительного кода при переходе на MPI может составлять 10–30% от исходного.
- Попытки создать более простые инструменты для прикладных программистов (физиков, химиков) пока не увенчались успехом.
- Производительность таких инструментов значительно ниже, чем у чистого MPI.

### 5.6. Применение MPI
- MPI — стандарт де-факто для кластерных систем.
- Используется в HPC (High Performance Computing).
- Позволяет создавать переносимые параллельные программы.
## 6. Дополнительные сведения о концепциях MPI (из транскрибации)

### 6.1. Популярность языков
- Стандарт MPI поддерживает три основных языка: **Fortran**, **C**, **C++**.
- Наиболее популярны C и Fortran; C++ используется меньше, но если считать C++ включающим C, то картина меняется.
- Библиотек написано огромное количество как на C, так и на Fortran.
- Все примеры в курсе рассматриваются на **C++** (с использованием C-стиля).

### 6.2. Типы операций передачи данных
- **Парные (point-to-point):** участвуют ровно два процесса — источник и приёмник.
  - Пересылка самому себе не имеет смысла и может работать некорректно.
  - Обязательно указывать коммуникатор.
- **Коллективные (collective):** участвуют несколько процессов (начиная с одного).
  - Даже одна операция может работать, если в коммуникаторе один процесс.
  - Примеры: `MPI_Bcast`, `MPI_Reduce`, `MPI_Scatter`, `MPI_Gather`, `MPI_Allgather`, `MPI_Alltoall`, `MPI_Allreduce`, `MPI_Barrier`.

### 6.3. Коммуникатор
- Служебный объект MPI.
- С точки зрения реализации — обычно число, сопоставленное с внутренней структурой.
- Для программиста не важно, как он устроен внутри.
- Каждый коммуникатор обозначается переменной (если создан вручную) или константой.
- Стандартный коммуникатор, создаваемый по умолчанию, — **`MPI_COMM_WORLD`**.
- Включает все процессы программы.
- Указывается во всех операциях передачи данных (обычно последний или близкий к последнему параметр).

### 6.4. Соглашение об именовании в MPI
- Все сущности MPI именуются по шаблону:
  - Префикс `MPI_`.
  - Далее отдельные слова разделяются символом подчёркивания.
  - Константы — заглавными буквами.
  - Имена функций и типов — с заглавной буквы в начале слов, остальное — строчными.
- Пример: `MPI_Init`, `MPI_Comm_size`, `MPI_COMM_WORLD`, `MPI_INT`.

### 6.5. Типы данных
- Обязательно указывать тип передаваемых данных.
- Базовые типы MPI соответствуют фундаментальным типам C и Fortran.
- Можно создавать производные типы данных (derived datatypes) для описания сложных структур.
- Специальный тип **`MPI_PACKED`** — для упакованных данных (фактически просто последовательность байтов).
- С точки зрения языка C тип `char` также можно считать базовым для упаковки/распаковки вручную.
- MPI предоставляет независимый от языка механизм описания данных.

### 6.6. Виртуальные топологии
- Логическая топология связей между процессами.
- По умолчанию — полный граф (любой может напрямую обратиться к любому).
- MPI позволяет задавать топологии в виде **решёток** (grid) произвольной размерности.
- Наиболее часто используются **двумерные решётки** (например, в алгоритмах умножения матриц).
- Топология **виртуальная**, не привязана к физической.
- Не запрещает передачи между любыми процессами, даже если они не являются «соседями» в топологии.
- Просто способ упростить описание того, кто с кем должен обмениваться в рамках алгоритма.
- Если вы не понимаете, зачем строить специальную топологию, — она, скорее всего, не нужна.

## 7. Основы MPI: инициализация и завершение

### 7.1. Структура MPI-программы

```c
#include "mpi.h"

int main(int argc, char *argv[]) {
    // Код без использования MPI (объявление переменных, констант)
    MPI_Init(&argc, &argv);
    // Код с использованием MPI
    MPI_Finalize();
    // Код без использования MPI (освобождение памяти, закрытие файлов)
    return 0;
}
```

**Пояснения:**
- Первый вызов MPI-функции — **`MPI_Init`**.
  - Прототип: `int MPI_Init(int *argc, char ***argv);`
  - Принимает адреса аргументов командной строки (как в `main`).
  - Нужен для того, чтобы реализация MPI могла внести изменения (например, передать аргументы между процессами).
- Последний вызов MPI-функции — **`MPI_Finalize`**.
  - Прототип: `int MPI_Finalize(void);`
  - Выполняет завершающие действия по использованию MPI.
  - Не является `return` — после него может выполняться код, не использующий MPI.
  - Должна вызываться **один раз**.
- Существует также **`MPI_Abort`** — аналог `exit`, для досрочного завершения.
- `MPI_Init` также вызывается **один раз**.
- Функции MPI могут вызываться не только из `main`, но из любого места программы.
- Заголовочный файл — **`mpi.h`** (подключается с кавычками, так как не является стандартным для языка).
- Путь к `mpi.h` задаётся в настройках сборки (CMake, командная строка и т.д.).

### 7.2. Запуск MPI-программы
- Запускается специальной утилитой, а не как обычная программа.
- Стандарт не определяет имя утилиты.
- Распространённые варианты: **`mpiexec`**, **`mpirun`**.
- Утилита имеет параметры, в том числе — какую программу запустить.
- Количество процессов задаётся при запуске.

### 7.3. Определение числа и ранга процессов

```c
int MPI_Comm_size(MPI_Comm comm, int *size);
int MPI_Comm_rank(MPI_Comm comm, int *rank);
```

- `MPI_Comm_size` — узнаёт количество процессов в коммуникаторе.
  - Если указать `MPI_COMM_WORLD`, вернёт общее число процессов.
- `MPI_Comm_rank` — узнаёт ранг текущего процесса в коммуникаторе.
  - Каждый процесс вызывает эту функцию и получает свой уникальный номер.
  - Нумерация начинается с **0**.
  - Ранги идут подряд: 0, 1, 2, ..., size-1.
  - Ранг не меняется в течение выполнения программы.
- Обычно вызываются сразу после `MPI_Init`.

**Пример:**
```c
#include "mpi.h"
int main(int argc, char *argv[]) {
    int ProcNum, ProcRank;
    MPI_Init(&argc, &argv);
    MPI_Comm_size(MPI_COMM_WORLD, &ProcNum);
    MPI_Comm_rank(MPI_COMM_WORLD, &ProcRank);
    // ...
    MPI_Finalize();
    return 0;
}
```

### 7.4. Распределение вычислений и данных
- После получения числа процессов и ранга можно распределять вычисления и данные.
- Пример: массив размером N делится на блоки.
  - Если N делится на число процессов без остатка — всё просто.
  - Если есть остаток — нужно предусмотреть обработку «хвоста».
- В MPI **нет автоматизации** распределения вычислений и данных (в отличие, например, от OpenMP).
- Всё прописывается вручную: циклы, условия, распределение блоков.

### 7.5. Минимальный набор функций MPI
Шесть функций, которых достаточно для написания любой MPI-программы:
1. `MPI_Init` — инициализация.
2. `MPI_Finalize` — завершение.
3. `MPI_Comm_size` — количество процессов.
4. `MPI_Comm_rank` — ранг процесса.
5. `MPI_Send` — отправка сообщения.
6. `MPI_Recv` — приём сообщения.

Всё остальное в MPI — для удобства, сокращения кода и повышения эффективности.

## 8. Операции отправки и приёма сообщений

### 8.1. Тройка параметров для описания данных
В большинстве операций передачи данных используется тройка:
- **`buf`** — адрес начала буфера с данными.
- **`count`** — число элементов данных.
- **`type`** — тип элементов данных.

Объём передаваемых данных = `count * sizeof(type)`.

Эта тройка присутствует как в парных, так и в коллективных операциях:
- либо для отправляемых данных,
- либо для принимаемых,
- либо для обоих.

### 8.2. Функция MPI_Send

```c
int MPI_Send(void *buf, int count, MPI_Datatype type,
             int dest, int tag, MPI_Comm comm);
```

- `buf` — адрес буфера с данными.
- `count` — число элементов.
- `type` — тип элементов.
- `dest` — ранг процесса-получателя (**destination**).
- `tag` — тег сообщения (целое число).
- `comm` — коммуникатор.

**Важно:**
- Программист сам следит за корректностью ранга получателя.
- Если указать несуществующий ранг — поведение зависит от реализации (ошибка, потеря данных и т.д.).
- В HPC-программах проверки минимизируют для производительности.
- Предполагается, что программа написана корректно.

### 8.3. Параметр tag
- Используется для идентификации сообщений.
- Позволяет различать сообщения при приёме.
- Порядок отправки у отправителя фиксирован.
- На приёме порядок можно менять, используя разные теги.
- Можно классифицировать сообщения (например, управляющие и данные).
- Если классификация не нужна — обычно указывают `0`.
- На приёме можно указать `MPI_ANY_TAG` — принимать сообщения с любым тегом.
- Если тег не совпадает — сообщение не будет принято.

### 8.4. Типы данных MPI для C
| MPI_Datatype | C Datatype |
|--------------|------------|
| MPI_CHAR | signed char |
| MPI_SHORT | short |
| MPI_INT | int |
| MPI_LONG | long |
| MPI_UNSIGNED_CHAR | unsigned char |
| MPI_UNSIGNED_SHORT | unsigned short |
| MPI_UNSIGNED | unsigned int |
| MPI_UNSIGNED_LONG | unsigned long |
| MPI_FLOAT | float |
| MPI_DOUBLE | double |
| MPI_LONG_DOUBLE | long double |
| MPI_PACKED | (упакованные данные) |

**Примечание:** таблица соответствует второму стандарту MPI. Для встроенных типов перечислено практически всё, кроме комплексных чисел.

### 8.5. Передача скалярных переменных и массивов
- Для передачи одной скалярной переменной:
  - `count = 1`,
  - `type` — соответствующий тип,
  - `buf` — адрес переменной.
- Для передачи массива:
  - `buf` — адрес начала массива,
  - `count` — число элементов,
  - `type` — тип элементов.
- Если указать `count` больше, чем размер массива, будет прочитана лишняя память (мусор).
- Проверок на корректность размера нет — программист сам следит за этим.

### 8.6. Функция MPI_Recv

```c
int MPI_Recv(void *buf, int count, MPI_Datatype type,
             int source, int tag, MPI_Comm comm, MPI_Status *status);
```

- `buf` — адрес буфера для приёма данных.
- `count` — число элементов.
- `type` — тип элементов.
- `source` — ранг процесса-отправителя.
  - Можно указать `MPI_ANY_SOURCE` — принимать от любого процесса.
- `tag` — тег сообщения.
  - Можно указать `MPI_ANY_TAG` — принимать с любым тегом.
- `comm` — коммуникатор.
- `status` — указатель на структуру с информацией о результате.

**Важно:**
- Буфер должен быть достаточным для приёма.
- Типы отправленных и принятых данных должны совпадать.
- `MPI_Recv` — **блокирующая** функция: процесс приостанавливается до получения сообщения.
- Если ожидаемое сообщение отсутствует — процесс блокируется.

### 8.7. Структура MPI_Status
- `status.MPI_SOURCE` — ранг отправителя.
- `status.MPI_TAG` — тег полученного сообщения.
- `MPI_Get_count(MPI_Status *status, MPI_Datatype type, int *count)` — возвращает число элементов типа `type` в полученном сообщении.

## 11. Детали работы MPI_Recv и MPI_Send

### 11.1. Выделение памяти перед приёмом
- Перед вызовом `MPI_Recv` должна быть выделена память, достаточная для размещения принимаемых данных.
- Иначе — ошибка, аналогичная ошибке в обычных программах при копировании данных по чужому/недостаточному адресу.
- Аналогично для `MPI_Send`: перед вызовом нужно создать буфер, заполнить его данными и отправить.

### 11.2. Параметр source в MPI_Recv
- `source` — ранг процесса-отправителя, от которого ожидается приём.
- Можно указать конкретный ранг.
- Можно указать **`MPI_ANY_SOURCE`** — принимать от любого процесса.
- Типичная схема:
  - Нулевой процесс — ведущий (master): читает данные из файлов, решает, какому процессу какие данные отдать, выполняет передачу через `MPI_Send` в цикле.
  - Каждый рабочий процесс принимает данные одним `MPI_Recv`, выполняет расчёт, отправляет результат обратно нулевому процессу.
  - У нулевого процесса — цикл из `MPI_Recv`.
- Если писать цикл последовательно (ждать от первого, потом от второго и т.д.) — может быть существенно дольше, чем если указать `MPI_ANY_SOURCE` и принимать от того, кто первым отправил.
- Это особенно важно, если рабочие процессы загружены неравномерно.
- Аналогично можно указать **`MPI_ANY_TAG`** — принимать сообщения с любым тегом.
- Либо указывать конкретный тег — тогда принимаются только сообщения с этим тегом.

### 11.3. Структура MPI_Status
- `status.MPI_SOURCE` — ранг процесса-отправителя.
- `status.MPI_TAG` — тег принятого сообщения.
- `MPI_Get_count(MPI_Status *status, MPI_Datatype type, int *count)` — возвращает число элементов типа `type` в принятом сообщении.
- На практике `MPI_Get_count` используется редко, так как при корректно написанной программе количество принятых данных известно заранее (`count * type`).

### 11.4. Ранги и коммуникаторы
- Ранг уникален в рамках конкретного коммуникатора.
- Один процесс может входить в разные коммуникаторы одновременно.
- В каждом коммуникаторе у процесса свой ранг.
- Ранги в разных коммуникаторах могут совпадать.
- В классических параллельных программах дополнительные коммуникаторы обычно не используются.
- В более сложных задачах может потребоваться управление коммуникаторами (создание, удаление).

### 11.5. Блокирующий характер MPI_Recv
- `MPI_Recv` — блокирующая функция.
- Процесс-получатель вызывает функцию и ждёт получения данных.
- Пока данные не приняты в количестве `count` элементов указанного типа, функция не завершается.
- Если указан неверный `source`, неверный `tag` или процесс-отправитель существует, но не отправил данные — процесс-получатель «висит».
- Дальнейшее поведение зависит от среды запуска:
  - Система управления кластером может завершить задачу по тайм-ауту.
  - При интерактивном запуске на персональном компьютере можно завершить процесс стандартными средствами ОС.
- Даже на одноядерных процессорах можно запускать несколько MPI-процессов — они будут взаимодействовать, но с ограничением по времени.
- На многоядерных процессорах процессы, скорее всего, будут распределены по разным ядрам — это реальное параллельное исполнение (без передачи по сети).

### 11.6. Блокирующий характер MPI_Send
- `MPI_Send` — тоже блокирующая операция, но завершается намного быстрее.
- Задача `MPI_Send` — не просто отправить данные, а сделать так, чтобы отправка когда-нибудь завершилась.
- Стандартный `MPI_Send` завершается в момент, когда данные скопированы во **внутренний буфер** MPI.
- У каждого процесса есть внутренний буфер некоторого размера для временного хранения отправляемых/принимаемых данных.
- После копирования в буфер работа `MPI_Send` закончена — runtime-часть MPI обеспечивает доставку.
- Если `MPI_Recv` был вызван — данные будут приняты. Если не был — логическая ошибка.

### 11.7. Функции измерения времени
- `MPI_Wtime()` — возвращает текущее время в секундах (тип `double`).
- `MPI_Wtime()` — редкий пример функции MPI **без параметров** (большинство функций имеют хотя бы коммуникатор).
- Вызывается дважды: до и после замеряемого кода. Разница — время выполнения в секундах.
- Преимущество: независимость от тактовой частоты, форматов и платформы.
- Точность измерения можно узнать с помощью `MPI_Wtick()`.
- Обычно точность — 1 микросекунда (на большинстве версий).
- Можно использовать стандартные функции языка C (`clock`) или ОС, но это снижает переносимость.

## 12. Первая программа на MPI (пример с приветствием)

### 12.1. Структура программы
```c
MPI_Init(&argc, &argv);
MPI_Comm_size(MPI_COMM_WORLD, &ProcNum);
MPI_Comm_rank(MPI_COMM_WORLD, &ProcRank);
if (ProcRank == 0) {
    printf("Hello from %d!\n", ProcRank);
    for (int i = 1; i < ProcNum; i++) {
        MPI_Recv(&ProcRank, 1, MPI_INT, MPI_ANY_SOURCE, MPI_ANY_TAG, MPI_COMM_WORLD, &status);
        printf("Hello from %d!\n", ProcRank);
    }
} else {
    MPI_Send(&ProcRank, 1, MPI_INT, 0, 0, MPI_COMM_WORLD);
}
MPI_Finalize();
```

### 12.2. Пояснения
- Нулевой процесс выполняет большую часть действий, остальные — исполнители.
- Если `ProcRank == 0` — выводится приветствие от нулевого процесса.
- Затем цикл от 1 до `ProcNum-1`: нулевой процесс ожидает получения ранга от каждого процесса.
- `MPI_ANY_SOURCE` — принимаем от любого процесса.
- Остальные процессы выясняют свой ранг и отправляют его нулевому процессу.
- Порядок приёма — произвольный, может меняться от запуска к запуску.

### 12.3. Важные моменты
- Код вне условных операторов выполняется **всеми процессами** одновременно (или почти одновременно).
- Если процессов больше, чем доступных ядер, — реального параллелизма может не быть.
- Если есть условие (`if (ProcRank == 0)`), то разные процессы выполняют разные ветки.
- Все процессы вызывают строку с проверкой, но попадают в разные ветки.

### 12.4. Вывод на экран (printf)
- Можно использовать стандартную `printf`.
- При запуске на персональном компьютере консоль доступна, все процессы могут использовать `printf`.
- Можно упростить программу, убрав условия, но тогда выводы от разных процессов могут **перемешаться**.
- Многие реализации MPI раскрашивают выводы от разных процессов, чтобы помочь.
- С вводом (`scanf`) ситуация сложнее:
  - Ввод возможен только с одного ранга.
  - Если вызвать `scanf` на нескольких процессах — может не работать.
  - Остальные процессы будут ждать данных, которых нет.
  - Обходной путь: файл ответов, из которого каждый процесс читает свои данные.
  - На практике ввод с консоли в MPI-программах избегают.
  - Параметры передают через аргументы командной строки или файлы.

### 12.5. Фиксация порядка приёма
- В примере порядок приёма не фиксирован.
- Можно изменить: указать конкретный процесс в `MPI_Recv`:
  ```c
  MPI_Recv(&ProcRank, 1, MPI_INT, i, MPI_ANY_TAG, MPI_COMM_WORLD, &status);
  ```
  где `i` — счётчик от 1 до `ProcNum-1`.
- Тогда порядок всегда будет жёстким: сначала от первого, потом от второго и т.д.
- Но этот вариант, скорее всего, будет **медленнее**, так как процессы выполняются с разными задержками.
- Вариант с `MPI_ANY_SOURCE` позволяет минимизировать задержки за счёт приёма от того, кто первым отправил.
## 15. Возвращаемые значения функций MPI

- Каждая функция MPI (за исключением `MPI_Wtime`, `MPI_Wtick` и некоторых подобных) возвращает **`int`**.
- Возвращаемый тип используется для передачи **статуса завершения**.
- По умолчанию возвращается **`MPI_SUCCESS`**, если всё хорошо.
- Если что-то пошло не так — возвращается другой статус.
- Набор возможных статусов можно найти в стандарте MPI или в заголовочном файле `mpi.h` (искать константы `MPI_SUCCESS` и рядом).
- Примеры ошибок:
  - неправильный коммуникатор,
  - неправильный ранг,
  - неправильный указатель на буфер и т.д.
- Конкретные реализации могут анализировать не все ошибки; если стандарт фиксирует обязательность проверки — она будет обеспечена, если нет — может не производиться.

## 16. Задача суммирования элементов вектора (продолжение)

### 16.1. Постановка задачи
- Нужно просуммировать элементы вектора (массива) из `n` чисел.
- Числа могут быть целыми или вещественными.
- Требуется параллельная реализация.

### 16.2. Схема параллельной реализации
1. Разделить данные на блоки.
2. Распределить блоки по процессам.
3. Каждый процесс суммирует свою часть.
4. Собрать частичные суммы на одном процессе.
5. Сложить их для получения общего результата.

### 16.3. Особенности MPI-программ
- MPI-программу можно запускать **в один процесс**.
- Тогда `size = 1`, `rank = 0`, и весь код должен работать корректно.
- Циклы, рассчитанные на несколько процессов, просто не выполняются.
- В идеале любую MPI-программу нужно писать так, чтобы она работала и в один процесс.
- Не всегда так бывает: иногда явно фиксируется схема «мастер-рабочий», требующая至少 двух процессов.
- В данном примере нулевой процесс тоже является расчётным (не только мастером).
- Нулевой процесс выступает в роли главного: распределяет данные, собирает результаты, но и сам участвует в вычислениях.

### 16.4. Распределение данных
- Предполагается, что `n % p = 0` (где `p` — число процессов).
- Размер блока для каждого процесса: `n / p`.
- Типичная ситуация: только у нулевого процесса есть информация о размере `n` и данные.
- Остальные процессы не могут даже выделить память, пока не узнают `n`.
- Нужно сначала сообщить всем процессам `n`.

### 16.5. Проблема эффективной рассылки `n`
- Изначально только у нулевого процесса есть `n`.
- Если использовать цикл `MPI_Send` от нулевого ко всем остальным — это **линейная** зависимость по времени.
- Более эффективный способ — **древовидная рассылка**:
  - Нулевой отправляет первому.
  - Теперь у двух процессов есть данные.
  - Нулевой отправляет второму, первый — третьему (одновременно).
  - Теперь у четырёх процессов есть данные.
  - И так далее.
- Время такой рассылки зависит от `p` **логарифмически**.
- Написать такой код вручную можно, но требует усилий.
- Поскольку ситуация типовая, в MPI есть стандартная функция — **`MPI_Bcast`**.

## 17. Функция MPI_Bcast (широковещательная рассылка)

### 17.1. Прототип
```c
int MPI_Bcast(void *buf, int count, MPI_Datatype type,
              int root, MPI_Comm comm);
```

- `buf` — адрес буфера с данными.
- `count` — число элементов.
- `type` — тип элементов.
- `root` — ранг процесса-источника (корень дерева).
- `comm` — коммуникатор.

### 17.2. Особенности
- **Коллективная операция**: все процессы коммуникатора должны её вызвать.
- Если в программе есть условные операторы, `MPI_Bcast` должен присутствовать во всех ветках.
- Все процессы должны вызвать функцию с **одинаковыми параметрами**.
- На процессе `root` буфер должен быть заполнен данными в количестве `count` элементов типа `type`.
- На всех остальных процессах буфер должен быть выделен в достаточном размере.
- Данные на остальных процессах будут затёрты принятыми данными.
- Порядок рассылки внутри реализации не важен — важно, что все получат копию.
- Реализация MPI сама выберет оптимальный способ (древовидная рассылка, учёт топологии и т.д.).
- В отличие от цикла `MPI_Send`, `MPI_Bcast` работает эффективнее (логарифмическая зависимость).

### 17.3. Учёт топологии
- Если программа запущена на нескольких узлах, и процессы расположены парами на одном узле:
  - Передача данных внутри узла дешевле, чем по сети.
  - Хорошая реализация MPI учтёт это и будет передавать данные внутри узла быстрее.
- Это ещё одна причина использовать `MPI_Bcast` вместо ручного цикла.

### 17.4. Статистика использования
- `MPI_Bcast` — **самая часто используемая функция** передачи данных в MPI.
- Типичная схема: исходные данные есть у одного процесса, их нужно разослать всем.
- Внутри реализации `MPI_Bcast` использует `MPI_Send` и `MPI_Recv`:
  - Листья дерева — только `MPI_Recv`.
  - Промежуточные узлы — и `MPI_Send`, и `MPI_Recv`.
  - Корень — только `MPI_Send`.

### 17.5. Схема работы
- До операции: данные только у `root`.
- После операции: у всех процессов коммуникатора есть копия данных.

### 17.6. Вопрос: можно ли использовать MPI_Bcast для рассылки половине процессов?
- **Ответ из двух частей:**
  1. Можно создать **дополнительные коммуникаторы** и разбить процессы на группы. В рамках каждой группы — свой `MPI_Bcast`.
  2. Можно использовать **точечные (point-to-point) операции** (`MPI_Send`/`MPI_Recv`) для выборочной рассылки.
- В исходном варианте `MPI_Bcast` для половины процессов не годится, так как он работает в рамках всего коммуникатора.

## 18. Итоги лекции 2 (полный обзор)

### 18.1. Коллективные операции
- **`MPI_Bcast`** — широковещательная рассылка.
- **`MPI_Reduce`** — редукция данных на одном процессе.
- **`MPI_Scatter`** — распределение данных по процессам.
- **`MPI_Gather`** — сбор данных со всех процессов на одном.
- **`MPI_Allgather`** — сбор данных всеми процессами.
- **`MPI_Alltoall`** — обмен данными между всеми процессами.
- **`MPI_Allreduce`** — редукция с результатом у всех процессов.
- **`MPI_Barrier`** — синхронизация вычислений.

### 18.2. Парные операции
- **Режимы взаимодействия:**
  - Стандартный (`MPI_Send`).
  - Синхронный (`MPI_Ssend`).
  - По готовности (`MPI_Rsend`).
  - Буферизированный (`MPI_Bsend`).
- **Неблокирующее взаимодействие:**
  - `MPI_Isend`, `MPI_Irecv`, `MPI_Issend`, `MPI_Ibsend`, `MPI_Irsend`.
  - Проверка завершения: `MPI_Test`, `MPI_Wait`, `MPI_Testall`, `MPI_Waitall` и др.
- **Совмещённые приём и передача:**
  - `MPI_Sendrecv`, `MPI_Sendrecv_replace`.
