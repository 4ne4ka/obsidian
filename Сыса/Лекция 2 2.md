# Конспект лекции: Введение в MPI (часть 1)

## Что такое MPI

**MPI (Message Passing Interface)** — это технология для разработки параллельных программ для систем с распределённой памятью. По сути, это сочетание:

1. **Стандарта** — существует несколько версий стандарта MPI.
2. **Библиотеки** — набор функций, реализующих стандарт.
3. **Реализации** — конкретное программное обеспечение, которое нужно развернуть на системе, чтобы запускать MPI-программы.

Чтобы воспользоваться MPI, нужно:
- Иметь реализацию MPI для конкретной сети/кластера.
- Развернуть её в виде **runtime** (среды выполнения) для запуска программ.
- Использовать её как библиотеку: подключать заголовочные файлы (например, для C++), компилировать программу с нужной реализацией.

## Для каких систем предназначен MPI

MPI предназначен для **распределённых систем**, которые состоят из отдельных компьютеров (узлов, серверов), связанных сетью. Ключевые особенности:

- На каждом узле — своя операционная система.
- Каждый узел — полноценный компьютер: свои процессоры, своя оперативная память, всё своё.
- С точки зрения стандарта неважно, какие ОС на разных компьютерах. На практике MPI обычно применяют в **кластерных системах**, где узлы однотипны и ОС одинаковая (чаще всего Linux, реже Windows).
- Были попытки использовать MPI под Windows (в том числе от Microsoft), но они не прижились.

Поскольку каждый компьютер самостоятелен, чтобы имитировать работу программы как единого целого, требуется дополнительная поддержка. Такие средства разрабатывались задолго до MPI. Когда создавался первый стандарт MPI, весь накопленный опыт учли — поэтому уже первая версия стандарта была очень хорошо продумана.

## Расшифровка названия

**MPI = Message Passing Interface** — интерфейс передачи сообщений.

Основной способ взаимодействия программ в MPI — **передача и приём сообщений**. Под сообщениями понимаются любые данные:
- Данные фундаментальных типов, аналогичных типам в поддерживаемых языках.
- Произвольные сложные структуры данных (либо средствами MPI, либо через упаковку/визуализацию и отправку).

Помимо передачи сообщений, в MPI есть и другие возможности управления, но передача сообщений — главный механизм. Большую часть API мы разберём по ходу лекций.

## Модель программирования: одна программа — много процессов

Программист пишет **одну программу** (одну сущность). Внутри неё с помощью обычных условных операторов (if/else) или операторов множественного выбора (switch) выделяются фрагменты, которые выполняют разные сущности.

В качестве такой сущности выступает **процесс**. Поскольку экземпляры MPI-программы запускаются потенциально на разных узлах, каждый со своей ОС, используется возможность, которую предоставляет ОС — процесс.

В момент запуска:
- Определяется, сколько процессов требуется.
- В зависимости от способа запуска, MPI может быть установлена:
  - на отдельном компьютере;
  - в классе с персональными компьютерами, связанными сетью (можно указать, какие компьютеры использовать);
  - на кластере (обычно под управлением системы управления кластером, есть оболочка для указания узлов, числа процессов на узел и других параметров).

**Итоговая модель:** одна программа, один программный код, внутри которого условия определяют, какие действия выполняет тот или иной процесс — начиная с одного и до всех запущенных.

## Операции передачи данных

MPI поддерживает несколько видов операций передачи данных. Они появлялись постепенно с новыми стандартами. Классификаций несколько — отличаются:
- назначением;
- количеством процессов, участвующих в операции;
- техническими и смысловыми особенностями, позволяющими выбрать конкретную операцию для конкретной ситуации.

## Стандарт и реализация

**MPI — это библиотека.** Должна быть реализация, подготовленная кем-то, чтобы можно было воспользоваться MPI. Реализаций много:
- свободно распространяемые;
- коммерческие;
- с разными характеристиками.

Организация, которая занимается стандартом (упоминается ссылка на стандарты и документы, доступные для скачивания и чтения — написано подробно, не слишком сложно).

### Совместимость

- До 5-го стандарта MPI требовал **совместимости на уровне программного интерфейса (API)**: определялось, какие типы и функции должны быть реализованы.
- MPI — библиотека в виде набора функций. Она перпендикулярна классам.
- Поддерживаемые языки: **C** и **Fortran** в первых версиях, затем добавлена поддержка **C++** (но объекты явно нигде не применяются).
- Есть объектные оболочки: **Boost.MPI** (C++), оболочки на **C#**, **Python** и другие. Лектор их не использовал; все примеры будут на **C++**.
- Начиная с 5-го стандарта добавлено требование **бинарной совместимости** (насколько это возможно). По мере появления реализаций 5-го стандарта, возможно, программы можно будет переносить без перекомпиляции.

### Версии стандарта

| Версия | Год | Примечание |
|--------|-----|------------|
| MPI-1 | 1994 | Первый стандарт. Начало работы — 1992, первый рабочий вариант — ноябрь 1993 (конференция SuperComputing). |
| MPI-2 | 1997 | Добавлены новшества. |
| MPI-3 | 2012 | Через 15 лет после второго. |
| MPI-4 | 2021 | |
| MPI-5 | 2025 | Последний на данный момент. |

Первый стандарт был настолько хорошо продуман, что им пользовались очень долго. Второй появился через 3 года, но реализации и переход на него заняли много времени. Последующие стандарты добавляли либо удобства, либо дополнительные возможности, которые часто можно обойти и без них.

**Основной материал лекций** будет касаться первого и второго стандартов (по большей части первого).

## Сложность MPI

С одной стороны, сложность разработки снижается:
- До MPI не было совместимости между разными вариантами распределённых систем.
- MPI быстро завоевал популярность и сейчас — стандартный инструмент для кластерных систем.

С другой стороны:
- Функций много — больше сотни (возможно, уже под две сотни).
- Параметров тоже немало.
- Много общего между блоками функций — разобравшись, можно понять устройство.
- Исходные программы приходится **модифицировать**, дописывать новый код. По некоторым оценкам, объём дополнительного кода — до 20–30% (в простых случаях — единицы процентов).

Регулярно предпринимаются попытки сделать что-то более простое для прикладных программистов (физиков, химиков и т.д.), но пока они не увенчались успехом. Главная проблема — **производительность**: программы, написанные не на чистом MPI, работают значительно медленнее (те же 20–30%, может быть больше). Для десктопных программ и телефонов это не критично, но для HPC это много, поэтому MPI до сих пор остаётся стандартом.

## Процессы, ранги, группы

- В процессе выполнения MPI-программы существует **некоторое количество процессов**.
- Каждый процесс — со своим адресным пространством, независим от остальных.
- Чтобы множество процессов имитировало одну программу, исполняя одну сущность, они взаимодействуют друг с другом через **передачу информации с использованием сетевых возможностей**.
- Программист **не должен заботиться** о том, где какие процессы располагаются, на каких компьютерах, как именно передаются данные. Всё делается на более высоком уровне с указанием абстрактных параметров: что за данные, откуда передать, куда передать, где принять.
- **Количество процессов** чаще всего фиксируется в момент запуска программы. Во втором стандарте появились возможности добавлять процессы, но на практике это редко нужно.
- Процессы **нумеруются**. Номер называется **рангом**. Ранг получается каждым процессом и больше никогда не меняется (кроме некоторых ситуаций, когда процесс может входить в несколько групп).
- По умолчанию все процессы включаются в одну **стандартную группу** (её название будет рассмотрено позже). Есть возможность создавать дополнительные группы.

## Ключевые термины для запоминания

- **MPI** — Message Passing Interface.
- **Ранг** — номер процесса.
- **Группа** — множество процессов; по умолчанию — одна стандартная.
- **Runtime** — среда выполнения MPI-программ.
- **Реализация** — конкретное ПО, реализующее стандарт MPI.
- **Кластер** — типичная система для MPI: однотипные узлы под управлением общей ОС, связанные сетью.
# Конспект лекции: Введение в MPI (часть 2)

## Четыре базовые концепции MPI

В основе MPI лежат **четыре концепции**:

1. **Тип операции передачи данных** — как мы хотим передавать данные (какие варианты поддерживает стандарт).
2. **Описание данных** — что за данные мы передаём/принимаем и как они устроены.
3. **Группа и коммуникатор** — кто участвует в операции.
4. **Виртуальная топология** — как логически организованы процессы.

### 1. Тип операции передачи данных

Операции делятся на два основных типа:

- **Парные (point-to-point, точка-точка)** — участвуют **два процесса**: один источник, один приёмник. Самому себе пересылать данные нет смысла, и не факт, что это будет правильно работать. Поэтому в парных операциях обязательно два участника.
- **Коллективные** — участвуют **несколько процессов**, начиная с одного (фактически, все коллективные операции способны работать и с одним процессом). В зависимости от операции это может быть:
  - распределение данных;
  - копирование данных;
  - сбор данных;
  - редукция (специальная операция);
  - и так далее.

### 2. Описание данных

В каждой операции пересылки мы описываем:
- что за данные хотим передать или принять;
- как они устроены.

Подробнее — в разделе про функцию `MPI_Send` (тройка параметров: буфер, количество, тип).

### 3. Группа и коммуникатор

- Все процессы объединяются в **группу** — это просто набор рангов от 0 до некоторого числа.
- Поверх группы вводится понятие **коммуникатора** — служебный объект MPI. Его внутреннее устройство не фиксировано стандартом (зависит от реализации). Обычно с точки зрения реализации это некое число, сопоставленное с внутренней структурой.
- Для программиста коммуникатор — **основной объект**, который должен указываться во всех операциях. Он определяет, кто входит в выполнение этой операции.
  - В коллективных операциях участвуют **все** процессы из указанного коммуникатора.
  - В парных — **выбранные** из этого коммуникатора (идентификатор — ранг).
- Коммуникатор обозначается либо переменной (если мы сами его создаём — такие возможности есть), либо специальной константой по умолчанию.
- **Стандартный коммуникатор**, автоматически создаваемый при запуске любой программы, называется **`MPI_COMM_WORLD`**. Он включает все процессы.
- Во всех операциях коммуникатор нужно указывать. Обычно это последний параметр (или близко к последнему).

**Соглашение об именовании в MPI:**
- Префикс `MPI_` (заглавные буквы).
- Дальше отдельные слова разделяются символом подчёркивания.
- Константы — все заглавными буквами.
- Имена функций и типов — первые буквы слов заглавные, дальше строчные.

**Про интеркоммуникаторы** (коммуникаторы, связывающие разные группы) лектор рассказывать не будет.

### 4. Виртуальная топология

- По умолчанию реализуется **полный граф**: любой процесс может напрямую обратиться к любому другому.
- Это **логическая** топология, никак не связанная с физической. Физическая топология может быть самой разной (полный граф вряд ли будет реализован физически).
- Виртуальная топология — это просто **способ упрощения описания** того, кто для кого является соседом, с кем должен обмениваться данный алгоритм.
- При этом передавать сообщения можно от кого угодно кому угодно, если это зачем-то потребуется. Но если вы не понимаете, зачем вам специальная топология — не строите её.
- Чаще всего применяют топологию в виде **решёток** (grid). Размеры — от единицы и дальше до произвольного числа.
- Наиболее характерный пример — **двумерные решётки**, применяемые в алгоритмах умножения матриц (блочные алгоритмы, где передачу данных выгодно описывать в терминах решётки).

- Поддерживаются три языка: **Fortran**, **C**, **C++**.

## Структура MPI: из чего состоит

### Заголовочный файл

- Для C-варианта все возможности MPI сведены в **один заголовочный файл** — `mpi.h`.
- Подключается как `#include <mpi.h>` (угловые скобки, поскольку это не стандартный файл языка).
- Нужно указать в настройках сборки (CMake и т.п.), где найти правильный `mpi.h`.

### Первая и последняя функции

- **`MPI_Init`** — первая MPI-функция, которую можно использовать. До неё можно объявлять переменные MPI-типов и использовать константы, но первый **вызов функции** должен быть `MPI_Init`.
  - Прототип: два аргумента, повторяющие аргументы `main` (`argc` и `argv`) с дополнительными указателями.
  - Передаём **адреса** этих двух аргументов (`&argc`, `&argv`), чтобы реализация могла внести изменения (например, передать командные строки между процессами).
- **`MPI_Finalize`** — последняя вызываемая функция при стандартном завершении (когда всё хорошо).
  - Это **не** `return` и **не** завершение выполнения. Это завершающие действия по использованию MPI. После неё может идти любой код: освобождение памяти, закрытие файлов и т.д.
  - Должна выполняться **один раз**. `MPI_Init` — тоже один раз.
  - Не обязательно вызывать из `main` — можно откуда угодно.
- **`MPI_Abort`** — аналог `exit` из программы, применяется при досрочном завершении / ошибках.

**Схема программы:**
```
#include <mpi.h>
// объявления
MPI_Init(&argc, &argv);
// код, использующий MPI
MPI_Finalize();
// код, не использующий MPI
// выход
```

Если программа завершается раньше по каким-то причинам — `MPI_Finalize` можно не вызывать (память всё равно вернётся ОС), но хороший тон — корректно всё завершать.

### Запуск программы

- MPI-программы запускаются **специальным образом**, не как обычные — через специальную утилиту.
- Стандарт **не определяет**, как она должна называться. Распространённые варианты: **`mpiexec`** (самый частый), есть и другие.
- У утилиты есть параметры: что запустить, сколько процессов, на каких узлах и т.д.

## Шесть функций «мини-MPI»

Лектор выделяет **шесть функций**, которых достаточно, чтобы написать **любую** MPI-программу («мини-MPI»):

1. `MPI_Init`
2. `MPI_Finalize`
3. `MPI_Comm_size`
4. `MPI_Comm_rank`
5. `MPI_Send`
6. `MPI_Recv`

Всё остальное в MPI позволяет сделать код **проще, короче и эффективнее** для конкретных задач передачи/приёма/распределения, но не является принципиально необходимым.

### `MPI_Comm_size`

- Позволяет узнать, **сколько процессов** входит в тот или иной коммуникатор.
- Если первым параметром указать `MPI_COMM_WORLD`, узнаем общее количество процессов, созданных при запуске.
- Второй параметр — указатель на переменную, куда вернут количество.

### `MPI_Comm_rank`

- Каждый процесс вызывает эту функцию и узнаёт, **какой ранг** ему достался в этом коммуникаторе.
- В `MPI_COMM_WORLD` ранги: 0, 1, ..., size-1.
- **Нумерация всегда с нуля**, ранги идут подряд и **никогда не меняются** — процессы никуда не мигрируют.

**Пример:**
```c
int size, rank;
MPI_Comm_size(MPI_COMM_WORLD, &size);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);
```

Имея эти данные, можно распределять вычисления и данные:
- есть массив размером N;
- делим N на число процессов;
- если N не делится нацело — остаётся «хвостик», который кому-то придётся дополнительно обработать;
- пишем цикл или условия, какую часть какому процессу обработать.

**Важно:** в MPI, в отличие от других технологий (например, OpenMP, которую будут изучать в следующем семестре), **средств автоматизации практически нет**. Распределение вычислений, циклов, данных — всё приходится прописывать **самостоятельно**.

## Функция `MPI_Send` — отправка сообщения

В большинстве операций передачи данных описание данных — это **тройка параметров**:

1. **Буфер** — адрес буфера, содержащего данные.
2. **Count** — число элементов.
3. **Datatype** — тип этих элементов.

Поскольку язык статически типизированный: `count × sizeof(type)` = общий объём в байтах. Именно это и будет пересылаться (по умолчанию; для сложных типов — интереснее, разберём позже).

Эта тройка присутствует в **подавляющем большинстве** операций — как парных, так и коллективных, либо в виде отправляемых данных, либо принимаемых, либо в более сложном варианте.

**Параметры `MPI_Send`:**

1. Буфер (адрес начала данных).
2. Count (число элементов).
3. Datatype (тип элементов).
4. **Destination** — ранг процесса-получателя (адресат).
5. **Tag** — тег сообщения.
6. **Communicator** — коммуникатор.

**Важно про корректность:**
- Программист сам должен следить, чтобы указанный ранг **существовал** в коммуникаторе.
- Пример ошибки: запустили 8 процессов (ранги 0–7), а в `destination` указали 8. Восьмого процесса нет. Поведение зависит от реализации: данные уйдут никуда, будет ошибка или что-то ещё.
- В HPC-программах **минимизируют количество проверок**, потому что они замедляют код. Предполагается, что мы пишем корректно.

### Тег (tag)

- Предпоследний параметр, целого типа.
- Используется для описания самой передачи и позволяет на приёме:
  - **менять порядок приёма** сообщений;
  - **классифицировать** сообщения (например, управляющие vs данные).
- Отправка происходит **в том порядке**, как написаны вызовы `MPI_Send` у отправителя — этот порядок не меняется.
- На приёме с помощью тегов порядок можно менять.
- Если не собираетесь классифицировать — обычно указывают **0**.
- На приёме можно указать специальную константу `MPI_ANY_TAG` — принимать сообщение с любым тегом. Либо конкретное число (например, 0), тогда примется только сообщение с этим тегом. Если не совпадёт — данных нет, принимать нечего.

### Типы данных

Для фундаментальных типов языка C предусмотрены соответствующие обозначения в MPI:
- `MPI_INT` — для `int`
- `MPI_FLOAT` — для `float`
- `MPI_DOUBLE` — для `double`
- `MPI_CHAR` — для `char`
- и т.д.

Отдельно — `MPI_PACKED` для упакованных данных (описание будет позже).

**Табличка** соответствует, скорее, второму стандарту; для встроенных типов там практически всё, кроме некоторых (например, long double).

### Примеры использования

- **Скаляр:** хотите передать одну переменную — указываете адрес переменной, count = 1, соответствующий тип.
- **Массив:** указываете адрес массива, count = число элементов, тип.
- **Ошибка:** создали массив на 10 элементов, а указали count = 20. Из памяти будет считано 20 элементов и отправлено. Результат зависит от того, как потом используете данные. Если обрабатываете только 10 — передали лишнее; если нет — мусор. **Проверок на это не предусмотрено.**

## Функция `MPI_Recv` — приём сообщения

**Параметры:**

1. Буфер — куда положить принятые данные.
2. Count — сколько элементов.
3. Datatype — тип каждого элемента.
4. **Source** — от кого ожидаем приём (ранг источника).
5. **Tag** — тег.
6. **Communicator** — коммуникатор.
7. **Status** — статус операции.

**Важно:**
- Перед вызовом `MPI_Recv` **должна быть выделена память**, достаточная для размещения данных. Иначе — ошибка (как в обычных программах: копирование в чужую память, порча кучи и т.д.).
- В `MPI_Send` перед вызовом тоже нужно создать буфер и заполнить его данными.

### Source — от кого принимаем

- Можно указать конкретный ранг.
- Можно указать специальную константу **`MPI_ANY_SOURCE`** — принимать от **любого** процесса.

**Типичная схема с `MPI_ANY_SOURCE`:**
- Нулевой процесс — **ведущий (master)**. Читает данные из файлов, решает, какому процессу какие данные отдать, выполняет передачу через `MPI_Send` в цикле.
- Каждый рабочий процесс принимает свою порцию, выполняет расчёт, отправляет результат обратно нулевому.
- У каждого рабочего — один `MPI_Send`, у нулевого — цикл из `size` приёмов.
- Если писать цикл последовательно (ждём от первого, потом от второго, ...) — это может быть **существенно дольше**, чем если использовать `MPI_ANY_SOURCE`: принимаем от того, кто первым успел отправить, не ожидая остальных.
- Особенно эффективно, если работа у разных процессов занимает разное время.

### Tag на приёме

- Можно указать `MPI_ANY_TAG` — принимать сообщение с любым тегом.
- Либо конкретный тег — тогда принимается только сообщение с этим тегом.

### Status

- Структура с набором полей.
- Можно не трогать, если не нужно.
- Применяется, когда мы **не знаем** заранее параметры приёма (например, при `MPI_ANY_SOURCE`).

**Что можно узнать из статуса:**
- `status.MPI_SOURCE` — ранг процесса, от которого пришли данные.
- Тег принятого сообщения (если использовали `MPI_ANY_TAG`; если указывали конкретно — и так известно).

### `MPI_Get_count`

- Функция, в которую передаётся адрес статуса, тип элементов и адрес целочисленной переменной.
- Возвращает, **сколько данных было принято**.
- Лектор на практике ни разу не применял: если всё корректно написано, то `count × type` — это размер данных, который мы и так знаем.

---

## Ключевые термины (часть 2)

- **`MPI_COMM_WORLD`** — стандартный коммуникатор, включающий все процессы.
- **`MPI_Init` / `MPI_Finalize`** — первая и последняя функции.
- **`MPI_Comm_size` / `MPI_Comm_rank`** — узнать число процессов и свой ранг.
- **`MPI_Send` / `MPI_Recv`** — парные операции отправки/приёма.
- **`MPI_ANY_SOURCE` / `MPI_ANY_TAG`** — константы для приёма от любого источника / с любым тегом.
- **Тройка описания данных:** буфер, count, datatype.
- **Тег** — классификатор сообщений, позволяет менять порядок приёма.
- **Виртуальная топология** — логическая организация процессов (по умолчанию — полный граф; часто — решётки).
- **Мини-MPI** — шесть функций, достаточных для написания любой MPI-программы.

# Конспект лекции: Введение в MPI (часть 3 — окончание)

## Ранги и коммуникаторы (дополнение)

- Ранг для каждого процесса **уникален в рамках коммуникатора**.
- Каждый процесс может входить в **разные коммуникаторы одновременно**.
- В рамках каждого коммуникатора у процесса **свой ранг**. Ранги в разных коммуникаторах могут совпадать, а могут и нет.
- В классических параллельных программах это обычно не используют — нет необходимости. В более сложных задачах может потребоваться управление коммуникаторами и создание дополнительных.

---

## Блокирующий характер `MPI_Recv`

- `MPI_Recv` — **блокирующая** функция: процесс-получатель вызывает её и **ждёт** получения данных.
- Пока данные не будут приняты в количестве `count` штук указанного типа, функция **не завершается**.
- Если указан неверный `source`, неверный `tag`, или процесс-отправитель существует, но данные не отправил — процесс-получатель **фактически висит**.
- Дальнейшее поведение зависит от того, где и как запущена программа:
  - Система управления кластером может снять процесс по **тайм-ауту**.
  - При интерактивном запуске (на своём компьютере) можно снять процесс стандартными средствами ОС из консоли.
- Даже на одноядерных процессорах можно было запускать несколько процессов — они взаимодействуют, только в режиме разделения времени. На многоядерных процессах они с большой вероятностью окажутся на разных ядрах — это реально параллельное исполнение (без передачи по сети).

---

## Блокирующий характер `MPI_Send`

- `MPI_Send` — **тоже блокирующая** операция по типу (есть блокирующие аналоги, которые будут рассмотрены на другой лекции).
- Но `MPI_Send` **завершается намного быстрее**, чем `MPI_Recv`.
- Задача `MPI_Send` — не просто отправить данные, а сделать так, чтобы отправка **когда-нибудь завершилась**.
- Стандартный `MPI_Send` завершается в момент, когда данные **скопированы во внутренний буфер** MPI.
- В реализации выделяется **некоторый буфер** на каждом процессе, в котором временно хранятся отправляемые/принимаемые данные.
- Задача `MPI_Send` — скопировать данные в этот внутренний буфер. После этого работа `MPI_Send` закончена, дальше **runtime-часть** обеспечит доставку.
- Если `MPI_Recv` был вызван — данные будут приняты. Не был вызван — логическая ошибка.

---

## Функции измерения времени: `MPI_Wtime` и `MPI_Wtick`

- Это **редкое исключение** — функции **без параметров** (у почти всех функций MPI есть хотя бы коммуникатор).
- Позволяют измерять время **независимым от языка и ОС способом**.
- Можно использовать функции языка C (например, `clock`) или ОС, но:
  - при использовании C-функций возникают нюансы в зависимости от компиляции;
  - при использовании функций ОС мы привязываемся к конкретной ОС, теряем переносимость.
- **`MPI_Wtime`** — возвращает значение типа `double`.
  - Вызывается **дважды**: один раз до замеряемого кода, второй раз после.
  - **Разница** между двумя вызовами — время в **секундах**.
  - Не зависит от тактовых частот и форматов конкретной платформы.
- **`MPI_Wtick`** — позволяет узнать **точность** измерения.
  - На большинстве версий возвращает **1 микросекунду** (1 миллионная секунды).

---

## Первая полноценная MPI-программа

Рассматривается программа, решающая более-менее связанную задачу. Структура:

```
MPI_Init(...);
MPI_Comm_size(MPI_COMM_WORLD, &size);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);
// ...
MPI_Finalize();
```

- Нулевой процесс выполняет **большую часть действий**.
- Все остальные — **исполнители**.
- Если `rank == 0` — выводится приветствие от нулевого процесса.
- Затем цикл от 1 до `size` — нулевой процесс ожидает получения сообщений от всех остальных.
- Остальные процессы выясняют свой ранг и **отправляют его** нулевому.
- В конце — `MPI_Finalize`.

**Важно:** фрагменты кода, **не находящиеся в условиях**, выполняются **всеми процессами одновременно** (или практически одновременно), если запущены на параллельной системе с достаточным числом исполнителей. Только в условиях разные процессы выполняют разные действия.

### Вывод на экран (`printf`)

- `printf` — стандартная функция. При запуске на своём компьютере доступна консоль, все процессы могут ей пользоваться.
- Можно было бы написать `printf` без условий, но тогда:
  - по умолчанию консоль связана с **любым** процессом (с любым рангом);
  - со всех остальных MPI должна доставить выводы на консоль;
  - в процессе доставки вывод может **перемешаться** — получится трудночитаемая мешанина.
- Многие реализации **раскрашивают** выводы от разных процессов, чтобы помочь.
- С `printf` хотя бы от любого процесса можно сделать вывод.
- С **функциями ввода** ситуация сложнее: ввод возможен **только с одного ранга**. Если вызвать `scanf` — с любого ранга, пожалуйста, а со всех остальных это может **не работать** (процессы зависнут в ожидании данных).
- Обходной вариант: **файл ответов** — заготовить ответы на все `scanf` и направить каждому процессу. Но на практике в HPC-программах так не используют.
- Параметры лучше передавать через **аргументы командной строки**; сложные данные — через **файлы**.

### Порядок приёма

- В рассмотренном примере порядок приёма **не фиксирован** — можно использовать `MPI_ANY_SOURCE`.
- Альтернатива: указать **конкретный процесс** (в цикле: сначала от первого, потом от второго и т.д.) — порядок будет **жёстким**, но, скорее всего, **медленнее**.
- Даже при параллельном исполнении процессы выполняются с разными задержками, поэтому произвольный порядок приёма помогает **минимизировать задержки**.

### Возвращаемое значение функций MPI

- Каждая функция MPI (кроме `MPI_Wtime`, `MPI_Wtick` и, может быть, ещё некоторых) возвращает **`int`**.
- Возвращаемый тип используется для **статуса завершения**.
- По умолчанию возвращается **`MPI_SUCCESS`**, если всё хорошо.
- Если что-то пошло не так — возвращается другой статус. Набор вариантов можно найти в стандарте или в заголовочном файле (константы, начиная с `MPI_SUCCESS`).
- Какие именно ситуации анализируются — определяется реализацией. Если стандарт фиксирует обязательность возврата — будет обеспечено; если нет — может не производиться.

## Коллективная операция: `MPI_Bcast` (broadcast, рассылка)

### Постановка задачи

Нужно просуммировать элементы вектора (массива) из N чисел. Распараллелить:
- раздать данные процессам;
- каждый процесс считает свою часть;
- собрать частичные суммы;
- выполнить итоговое сложение.

**Типичная ситуация:** исходные данные есть **у одного процесса** (обычно нулевого), у всех остальных изначально информации нет. Остальные процессы не могут даже выделить память, если она динамическая — не знают, сколько данных.

### Наивное решение через `MPI_Send`/`MPI_Recv`

- Нулевой процесс отправляет N первому.
- Теперь у двух процессов есть данные.
- Нулевой может отправить второму, первый — третьему **одновременно**.
- Дальше — каждый, у кого есть данные, отправляет ещё не охваченным.
- Итого: **древовидная схема**, время зависит от числа процессов **логарифмически**, а не линейно.
- Написать такой код можно, но **требует усилий**.

### Решение: `MPI_Bcast`

Поскольку ситуация типовая, есть **стандартная функция** — `MPI_Bcast` (broadcast, рассылка).

**Параметры:**
1. Буфер.
2. Count (число элементов).
3. Datatype (тип).
4. **Root** — источник (корень дерева), у кого исходно были данные.
5. Communicator.

**Смысл параметров зависит от того, какой процесс выполняет функцию:**
- На **root**: буфер должен существовать и быть заполнен данными в количестве `count` элементов типа `type`.
- На **всех остальных**: буфер должен быть **выделен в достаточном размере**. Данные там могут быть любыми (мусор, старые значения) — они будут **затёрты**.
- Всем, кроме root, в буфер будет скопировано `count` элементов типа `type`.

**Правила вызова:**
- **Все процессы коммуникатора** должны вызвать эту функцию с **одним и тем же набором параметров**.
- Если в программе есть условия — `MPI_Bcast` должен присутствовать **во всех ветках**.
- Все процессы рано или поздно должны вызвать функцию.

**Как это работает внутри:**
- Реализация использует `MPI_Send` и `MPI_Recv` внутри.
- Одни процессы (листья условного дерева) вызывают только `MPI_Recv`.
- Другие (не листья) — и `MPI_Recv`, и `MPI_Send`.
- Root — только `MPI_Send`.
- Порядок копирования **неизвестен** — реализация сама решает, как эффективнее.
- Это делается **максимально эффективно** (по типу greedy).

**Преимущества перед циклом `MPI_Send`:**
- В цикле — **линейная** последовательность.
- В `MPI_Bcast` — **логарифмическая** (древовидная).
- Многие реализации учитывают **физическую топологию**: если процессы на одном узле — передача внутри узла дешевле, чем по сети. Если реализация способна это использовать — будет быстрее.

**Популярность:**
- `MPI_Bcast` — **самая часто используемая** функция рассылки/приёма данных в MPI (по статистике).
- Причина: типичная схема, когда исходные данные есть у одного, и их нужно разослать.

**Схема:**
- Любой процесс из коммуникатора может быть root.
- После выполнения `MPI_Bcast` у **всех** процессов будет **копия данных**.

### Вопрос из зала: а если нужно послать только половине узлов?

Ответ из двух частей:
1. Можно создать **дополнительные коммуникаторы** и разбить процессы на две части (одна половина, другая). Тогда в рамках каждого коммуникатора можно взаимодействовать с частью процессов.
2. Можно использовать **коллективные операции** (например, scatter/gather), которые выполняют распределение данных так, чтобы кому-то ничего не послать. Это странно, но возможно.

В целом `MPI_Bcast` в начальном варианте для такой задачи **не годится**, потому что он работает по схеме «1 → всем».

## Ключевые термины (часть 3)

- **Блокирующие операции** — `MPI_Send` (завершается после копирования в буфер) и `MPI_Recv` (ждёт получения данных).
- **`MPI_Wtime` / `MPI_Wtick`** — измерение времени в секундах и точности измерения.
- **`MPI_SUCCESS`** — статус успешного завершения функции.
- **`MPI_Bcast`** — коллективная операция рассылки данных от одного процесса всем остальным.
- **Root** — процесс-источник в коллективной операции.

- **Ввод** возможен только с одного ранга; **вывод** — со всех, но может перемешиваться.
- **Аргументы командной строки и файлы** — предпочтительные способы передачи данных вместо консоли.
